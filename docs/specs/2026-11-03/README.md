## Основные решения

- Сохранить одну VPS. Второй собственный узел — альтернативная архитектура вне базового бюджета, а не скрытое обязательное условие плана.
- VK оставить действующим обходным путём; DNS — независимым резервом и способом доставки небольших настроек.
- AWG добавить для скорости при доступном прямом UDP-пути. Он не заменяет relay при полной блокировке IP VPS.
- В первую очередь убрать зависимость обновления от прямой доступности панели и обеспечить безопасное первое подключение.
- Пользовательская и административная сборки используют общий сетевой код. Сначала не переписывать ядро.
- SFU/WebRTC без браузера — первый новый экспериментальный relay; CDN/XHTTP — условный резерв после проверки доступности edge. Не включать экспериментальные способы в автоматический выбор до испытаний.
- 8 — текущий административный предел устройств, **не доказанная ёмкость VPS**. Расчёт возможен только как диапазон до профилирования.

## Термины и границы обещаний

«Нет интернета» различать как: нет физического канала; доступен только список адресов; недоступна только VPS; доступен транспорт, но не панель; истекли настройки. Эти состояния требуют разных действий.

«Ссылка» различать как: приглашение VPNN, адрес API, ссылка конференции VK, краткоживущие TURN-реквизиты. Одна постоянная ссылка пользователя не делает все эти сущности бессрочными.

Текущее пользовательское подтверждение «VK устраивает» принято как положительный полевой отзыв. Оно не заменяет нагрузочное измерение, проверку IPv6, длительности, устройства и оператора.

## Правила выполнения следующего этапа

Работа последовательно, без субагентов. Сначала локальная реализация и изолированные проверки. Системный VPN Windows запускает владелец. Рабочий VPS, существующий iPhone/KIT-контур, публикация релиза и создание внешних сервисов требуют отдельного согласованного этапа. Не переносить секреты в документы/публичные зеркала. Старые спецификации сохраняются как история; актуальное состояние описано в документе 01.
