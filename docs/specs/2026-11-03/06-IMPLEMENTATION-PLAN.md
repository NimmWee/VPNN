# 06. VPNN — последовательный план реализации

> Для исполнителя: использовать последовательное выполнение плана (superpowers:executing-plans). Без субагентов. Этот документ не разрешает начинать реализацию в текущем исследовательском этапе.

**Цель:** простой клиент Android/Windows с устойчивой доставкой настроек, автоматическим резервом и проверенной ёмкостью одной VPS.

**Архитектура:** общий Flutter/mihomo клиент с двумя сборками, один владелец TUN, подписанная конфигурация и индивидуальный серверный доступ. Сначала улучшить существующие VK/DNS, затем AWG; новые relay изолировать как эксперименты.

**Стек:** Dart/Flutter, Go, Python deployment, существующий nginx/systemd. Планы ниже ссылаются на требования документов 02–04; исследовательские гипотезы — документ 05. Пути относительно C:/VPNN. Новые имена файлов являются проектными предложениями.

## P6. Доступ при блокировке прямого IP

Дополнение из ТЗ `PAMPARAAAAAAM.md`. Приоритеты P0/P1 внутри ТЗ относятся к провайдерам SFU, поэтому здесь обозначены P6-A/B/C. Базовый выпуск сохраняет прежние критерии. Для приёмки расширения по этому ТЗ нужен минимум один работающий новый SFU-транспорт; второй провайдер — следующая цель реализации. Предварительные сведения об upstream и доступности платформ предстоит проверить.

Все собственные серверные компоненты и выход в интернет остаются на одной VPS. Клиент использует существующий TUN. Сторонняя инфраструктура переносит данные, а защита полезного трафика и аутентификация устройства действуют между клиентом и VPS. Прототип может использовать локальный SOCKS. Для интеграции сначала проверить расширение текущего runtime и адаптер Go/Pion, затем совместимость с mihomo, Android bindings и при необходимости управляемым процессом Windows.

- [ ] **P6-A — аудит и общие критерии.** Сверить `engine/runtime.go`, `engine/config.go`, `client/core/vpnn.go`, клиентские policy/health и схемы Control/deploy. Зафиксировать владельца жизненного цикла, границы адаптера, доставку параметров сессии, угрозы, откат и единый формат измерений. Проверить исходники, закрепить ревизию и лицензии `whitelist-bypass` и Slipstream. Планировать легитимный вход, ручную CAPTCHA и безопасное хранение учётных данных.
- [ ] **P6-B — Telemost и WB Stream.** Для Telemost проверить DataChannel и, при поддержке, VP8/RTP; для WB Stream проверить LiveKit/SFU, требования к видеотреку и установлению сессии. Изолированные прототипы можно готовить параллельно. Первым провести сквозную проверку варианта с подтверждённой доступностью и меньшим риском, затем второго независимого провайдера. Проверить передачу данных через headless Creator и публичный egress VPS при заблокированном прямом TCP/UDP к ней. Доступность SFU и успешный звонок сами по себе критерию не отвечают.
- [ ] **P6-C — Slipstream.** Отдельный адаптер и тестовый резолвер/зона без конфликта с UDP 53. Проверить совместимость с текущей DNS-инфраструктурой. Сравнить с зафиксированным MasterDnsVPN при одинаковых потерях, задержке и ограничениях частоты. Записать download/upload, RTT, DNS-запросы на МБ, повторы, потери, CPU/RAM и смену сети. Несколько резолверов проверять только при поддержке и фактической доступности. При отсутствии выигрыша сохранить MasterDnsVPN и записать причины.
- [ ] **P6-D — общая интеграция.** Назначить одного владельца изменений в `engine`, `client/core`, `client/lib/vpnn`, Control и deploy. Переиспользовать текущие Auto, подпись, идентификацию и отзыв. Согласовать подписанные параметры сессии, проверку готовности и реального HTTPS через VPS, состояния подключения и деградации, backoff и гистерезис, смену сети, временную потерю VPS и очистку старой сессии. Доставлять параметры через действующий канал или подписанный кэш. Показать фактический маршрут и причину сбоя, скорость и время соединения разместить там, где они нужны для диагностики. Сохранить Direct, VK TURN и MasterDnsVPN.
- [ ] **P6-E — ресурсы и приёмка.** Проверить модель Creator/Joiner, замерить память и CPU на активную сессию, ограничить число сессий и параллельных проверок, буферы, очереди и перезапуски. Проверить справедливое распределение, зависание, управляемый Stop и освобождение ресурсов. Воспроизвести локально блокировку прямого IP, обрывы, лимиты, несколько устройств, смену сети, отзыв, просроченные данные и неправильные подписи. На согласованном прогоне подтвердить публичный egress VPS и безопасный предел сессий, затем отдельно проверить физический Android в операторской сети. Итог — PASS/FAIL/NOT TESTED по 14 критериям ТЗ с доказательствами, сравнительная таблица VK/DNS/Telemost/WB/Slipstream и инструкция сборки, запуска, диагностики и отката.
- [ ] **Дополнительные варианты.** DION, Bitrix24 и Blink исследовать после первых двух провайдеров при воспроизводимой авторизации и практической пользе. CDN/XHTTP — отдельный эксперимент по согласованию. Для каждого решения записать версию, условия, зависимости, метрики и причину принятия или отказа.

### Параллельная работа

| Поток | Можно начать одновременно | Граница работы |
| --- | --- | --- |
| Telemost | Аудит upstream, DataChannel/VP8 и отдельный прототип | Свои рабочая копия, учётная запись или выделенная комната, порты и логи |
| WB Stream | Аудит LiveKit и отдельный прототип | Свои рабочая копия, тестовая сессия, порты и логи; без правок общего runtime |
| DNS | Анализ MasterDnsVPN, P3 fake-resolver тесты, прототип Slipstream | Выделенные порты, тестовый резолвер и зона; baseline зафиксировать до сравнительных замеров |
| P0/P3 и приёмка P2 | Методика, анализ сохранённых логов, матрица операторов, тесты отчёта и сценарии приёмки | Одна версия схемы метрик, отдельные файлы каждого прогона, исходные результаты только для чтения |
| Безопасность и поставка | Модель угроз, тестовые сценарии, проверка архивов и инструкция отката | Синтетические ключи и кэш; общую схему и интеграционные правки согласовать с P6-D |

Для параллельного выполнения использовать раздельные рабочие копии с собственными build/output и временными данными. У каждого прогона свой ID, каталог логов, фикстуры, устройство и подписанный тестовый доступ. Один AVD/serial, один телефон, один Windows TUN и общие выходы Flutter/Gradle/gomobile использовать по очереди; отдельные сборки параллелить только при проверенной изоляции каталогов и нативных выходов. Замеры скорости и CPU/RAM на одной VPS и из одной операторской сети проводить по очереди при одинаковых условиях. Отзыв выполнять только на выделенном тестовом устройстве после завершения его позитивных сценариев. Правки общих схем, Auto и runtime, применение на VPS и общую регрессию вести последовательно. Рабочая VPS, порты, firewall, SSH и сторонние работающие VPN требуют отдельного согласования изменений.
