# 04. Производительность и бюджет единственной VPS

Статус: расчёт по сохранённым данным и план испытаний. В этом этапе нет нового SSH-замера, CPU-модель, vCPU, квота и полоса не установлены. Нельзя подставлять характеристики рабочего Windows-компьютера вместо VPS.

## Известный серверный снимок

Источник: `logs/production-health-final.json`, предыдущая серверная проверка, не текущая телеметрия.

| Показатель | Значение |
| --- | ---: |
| MemTotal | 984568 KiB = 961,49 MiB |
| MemAvailable | 453528 KiB = 442,90 MiB |
| Total − Available | 518,59 MiB |
| SwapFree | 0 KiB; наличие/размер swap отдельно не установлены |
| Включённые устройства DNS/VK | 2 / 2 |
| Node sync restarts | 0 на момент снимка |

Total − Available не равно сумме RSS процессов: участвуют ядро, cache и доступность освобождения памяти. Использовать MemAvailable и memory.current/PSS, а не складывать RSS с повторным учётом разделяемых страниц.

## Расчёт запаса

Предлагаемый резерв ОС и всплесков — 200 MiB MemAvailable. Это инженерный порог для пилота, не свойство Linux. Из текущего снимка остаётся **242,90 MiB** для расширения поверх уже работающего набора.

Модель: `добавочная память = число новых DNS-доступов × idle DNS backend + число новых активных клиентов × активные буферы + новые службы`. Все коэффициенты нужно измерить. DNS backend запускается на каждый включённый DNS-доступ, даже без передачи. Для группы из 8 вместо текущих 2 добавляются 6 таких экземпляров, если сохранить архитектуру.

Сценарии ниже — **чувствительность расчёта, не измеренные потребления**. В столбце на устройство объединены idle backend и активные буферы:

| Допущение на дополнительное устройство | 6 устройств | Остаток Available без новых служб | С дополнительными службами 60 MiB |
| --- | ---: | ---: | ---: |
| 15 MiB | 90 MiB | 352,90 MiB | 292,90 MiB |
| 30 MiB | 180 MiB | 262,90 MiB | 202,90 MiB |
| 50 MiB | 300 MiB | 142,90 MiB | 82,90 MiB |

60 MiB — условный бюджет эксперимента, не прогноз SFU/AWG. При таком резервировании средний допустимый прирост на каждое из 6 устройств составляет `(442,90 − 200 − 60)/6 = 30,48 MiB`. Если реальный прирост больше, 8 устройств не проходят выбранный запас даже до CPU-ограничений.

Вывод: простой интерфейс и логика настроек почти не требуют дополнительных серверных служб; AWG на одном VPS выглядит кандидатом для пилота. Совместное размещение всех новых relay/SFU/Tor-процессов не обосновано. Headless не означает автоматически малую RAM. Постоянный Chromium/Electron и сборка исходников на этой VPS не входят в рекомендуемую схему.

## CPU, канал и трафик

Сохранённые ~61 MiB RSS и 0,55 CPU-секунды из VK-бенчмарка относятся к клиенту Windows с Xray, не к VPS. Их не использовать как серверную стоимость клиента.

Если целиться условно в 4 Мбит/с полезного download на каждого, то 2/4/8 активных клиентов требуют 8/16/32 Мбит/с полезной суммарной передачи. С условными накладными расходами 25–50% сценарий 8 пользователей даёт 40–48 Мбит/с на соответствующем внешнем направлении. Фактическое отношение wire/goodput измерить; DNS из-за дублирования и малых пакетов может отличаться намного сильнее.

VPS получает данные с сайтов и отправляет их к relay/клиентам, поэтому учесть обе стороны интерфейса и метод учёта трафика хостером. 8 × 4 Мбит/с × 2 часа/день × 30 дней / 8 = **864 GB полезного download в месяц**, без overhead и upload. Если тарифицируют ingress+egress, учёт может приблизиться к удвоенному объёму плюс накладные расходы. Лимит тарифа пока неизвестен.

6 VK-сессий × 8 клиентов = 48 сессий. Это не лимит TCP-потоков внутри и не гарантированная цена по RAM: число пользовательских потоков тоже важно. CPU измерять по ядрам, quota, steal, softirq и p95 задержке; общий процент CPU может скрыть одно насыщенное ядро.

## План измерений CAP

CAP-01: read-only inventory VPS: MemTotal/Available, CPU/vCPU/quota, swap, disk, inode, сеть, systemd/cgroups, PSS/FD каждой собственной и legacy-службы, NIC drops, conntrack, idle baseline 10 минут. Не выгружать конфиги/секреты.

CAP-02: отдельно зарегистрированные устройства 2→4→8 без трафика; затем активные 1→2→4→8. На каждом шаге три повторения ограниченной передачи в обоих направлениях, одна длительная передача, параллельно небольшие HTTPS-запросы. Повторить VK, DNS, смешанный режим, позднее AWG. Устройства с отдельными правами; общий ключ не использовать.

CAP-03: измерить latency p50/p95, TTFB, goodput каждого и агрегат за общую стеновую длительность, retransmits, ready sessions, CPU/PSS/FD/queues/packet drops, restarts. Сумма медиан не является агрегатным измерением.

CAP-04: ограничения первого пилота: остановить увеличение нагрузки при MemAvailable <200 MiB более 30 секунд, OOM, рестарте, устойчивом росте очередей, CPU насыщении с деградацией p95 более 2× контроля. Это proposed gates; откалибровать по baseline. Не убивать пользовательские процессы для освобождения ресурсов.

CAP-05: 2 часа на достигнутой устойчивой ступени, потом 24 часа смешанного использования. Искать рост памяти/FD после завершения нагрузки. Число поддерживаемых пользователей устанавливается по худшему из RAM/CPU/канал/relay/отзыв, а не по текущему max-active-devices.

## DNS: что именно исследовать

Исходные данные [отчёта 0.1.3](../../PERFORMANCE-0.1.3.md): download MTU 500, upload MTU 98, ARQ window 600, duplication 2. На 1 МиБ наблюдались 1,31–2,95 Мбит/с; upload 1 Мбит/с со слов пользователя не является новым лабораторным замером. Повышение MTU до согласованных 882 не дало устойчивого выигрыша; duplication=1 ухудшило результат. Сохранить defaults до новых доказательств.

При payload 98 байт 1 Мбит/с означает примерно 1276 порций/с, 5 Мбит/с — 6378; при дублировании до двух копий исходящая нагрузка может быть близка к удвоенной, ещё без control/ACK. Это оценка порядка величины, не пакетный capture. Для download 500 байт 1 Мбит/с — около 250 порций/с. Нельзя заключать, что все эти порции равны одному DNS datagram без проверки фрагментации.

DNS-01: per-resolver полезный payload, запросы/с, ответы/с, RTT/p95, loss, SERVFAIL/TC, reordering, доля пустых polling ответов, time-in-queue, согласованное окно и серверные лимиты.

DNS-02: сравнить доступный DNS оператора и небольшой список разрешённых публичных резолверов. Не массовое сканирование интернета. Использовать полные передачи, а не ICMP или только TXT latency. Менять стратегию распределения и исключения медленного пути по одной группе параметров.

DNS-03: исследовать polling/adaptive in-flight и pacing. На хорошем пути увеличить загрузку до начала роста потерь; при idle уменьшить частоту для батареи. Не увеличивать одновременно MTU, окно и параллелизм.

DNS-04: длина индивидуального домена сокращает upload payload. Оценить компактный label/заголовок только с сохранением индивидуальной аутентификации, маршрутизации и отзыва; потребуется совместимая серверная миграция. Не сокращать секрет/не заменять ключ общим ради скорости.

DNS-05: проверить, ограничивают ли производительность серверные workers=1, MAX_CONCURRENT_REQUESTS=512 и очереди256 в текущем per-device backend. Это гипотеза из deploy/node_sync.py, не установленная причина.

DNS-06: отдельный сравнительный Slipstream original/Rust и DNSTT стенд при одинаковых домене/длине имени, резолвере, сети, шифровании и полезном объёме. Новые серверные бинарники не заменяют текущий UDP53 без согласованной схемы демультиплексирования.

Принимать улучшение при повторяемом выигрыше сверх разброса и без деградации ошибок, интерактивности и RAM. Начать с трёх повторов, при шуме увеличить выборку; порядок A/B чередовать. Отдельно маркировать эмулятор, synthetic, Windows SOCKS и физический МегаФон.
