## Конкретный объём будущего согласования VPS

1. Проверить текущие service properties без выгрузки секретов: control использует существующие state/signing/admin-secret, node-sync здоров, версия applied совпадает с опубликованной. Снять бинарный SHA, права и владельца.
2. Создать root-only backup прежнего control-бинарника и защитную копию state/signing. Секреты не выводить и не переносить в публичные артефакты.
3. Передать только новый бинарник, проверить SHA-256, выставить прежние права/владельца, заменить файл атомарно в `/opt/vpnn-control/vpnn-control`.
4. Перезапустить **только** `vpnn-control`. Unit, nginx, DNS, VK relay, Xray, legacy/iPhone и node-sync код не менять. Проверить health и что node-sync применил новую версию без рестартов data-plane служб.
5. Откат при ошибке: вернуть прежний бинарник, перезапустить только control. **Не возвращать старый state поверх актуального**: `control.Open()` повышает version и сохраняет state при каждом запуске, а клиенты уже могли запомнить новый floor. Сохранённые state/signing — аварийный backup, не обычный шаг rollback.

Риск: перезапуск control кратковременно прерывает API и сбрасывает admin-сессии; startup повышает версию настроек. Новая версия state будет замечена reconciler. В текущем коде неизменные клиенты/ключи не вызывают restart общих data-plane служб, но это подлежит проверке по их NRestarts до/после. Нулевой перерыв пользовательских подключений до испытания не обещается.

Согласование этого этапа не разрешает менять состав устройств. Выдача/отзыв отдельного тестового доступа согласовываются отдельно: текущий reconciler может перезапустить общие VK/Xray службы при изменении allowlist/clients.

## Проверка в эмуляторе

1. Чистая установка debug-пакета в новый AVD; подписанный bootstrap через существующий доверенный приватный файл. Проверить его подпись/срок; просроченный пакет не продлевать вручную.
2. Блокировать direct VPS только внутри нового гостя, с уникальным комментарием firewall. Импортировать bootstrap и установить VK. Не затрагивать firewall Windows.
3. Получить конфигурацию через новый pinned HTTP listener. Диагностика должна показать выбранный маршрут vk и проверенную версию; сетевой контроль должен подтвердить запрещённый direct.
4. Повторить отдельно для DNS. Проверить Stop/отмену, смену сети гостя и перезапуск приложения без снятия direct-блокировки.
5. После согласованного обновления control получить новую подписанную версию по обоим путям; проверить сохранение и повторный старт с кэшем.
6. Отзыв проверять только на согласованном тестовом доступе. Новый подписанный ответ должен очистить основной кэш и журнал, а повтор старого bootstrap/кэша — отклоняться. До этого signed-revocation считается подтверждённым только локальными тестами.
7. Удалить только созданные этим тестом гостевые firewall-правила, завершить только собственный новый AVD. Сохранить обезличенные результаты.

## Что нужно от владельца

- Доступ для read-only SSH уже получен. Повторно присылать пароль не нужно.
- Явное согласование описанного выше обновления **только control** с кратким перерывом API и бинарным откатом.
- Указать тестовый доступ, который допустимо отозвать, и согласовать возможный краткий перезапуск общих relay/egress при изменении доступа. До этого можно проверять получение настроек по существующему тестовому доступу, если он ещё действителен.
- Windows и Honor отложены; результаты эмулятора не выдаются за физические/операторские проверки. Публикация остаётся отдельным решением владельца.
