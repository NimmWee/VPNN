# 05. Доступ к VPS при блокировках: исследование

Дата проверки источников: 2026-11-03. Метод: документация разработчиков, README проектов, исследовательская публикация и открытые обсуждения GitHub/NTC. Новые инструменты не запускались, чужие скрипты не устанавливались. Публичные утверждения о скорости не являются измерениями VPNN. Полный аудит кода каждого проекта не проводился.

Уровни: **A** — собственное испытание VPNN; **B** — механизм подтверждён первичным исходником/документацией, пригодность здесь не испытана; **C** — наблюдение участника форума в конкретной сети; **D** — проектная гипотеза. README с обещанием «невозможно заблокировать» не принимается доказательством.

## 1. Почему ping недостаточен

ICMP Echo может быть запрещён сервером или сетью при работающем TCP443/UDP. Промежуточные узлы traceroute также могут не отвечать, продолжая пересылку. Определять проблему по последнему отвечающему hop нельзя.

Диагностическая матрица будущего теста: ICMP как вспомогательный сигнал; TCP connect к собственному слушающему порту; TLS с правильным именем/сертификатом; HTTPS небольшой и затем ограниченный более крупный объект; валидный handshake выбранного UDP-протокола; DNS delegation через нужный резолвер; всё отдельно IPv4/IPv6. Отсутствие ответа на случайный UDP packet не доказывает блокировку. Для установления стороны потерь нужны согласованные captures клиента/сервера и контроль firewall/listener.

Классы: (a) только ICMP; (b) DNS-подмена; (c) фильтр SNI/протокола; (d) ограничение после некоторого объёма; (e) блок IP/CIDR; (f) строгий список доступных направлений; (g) физическое отсутствие канала; (h) отказ VPS. У разных операторов/регионов возможны разные сочетания.

В обсуждении [net4people #490](https://github.com/net4people/bbs/issues/490) автор описывает остановку передач после небольшого объёма и позднее добавляет наблюдения о CIDR. [#516](https://github.com/net4people/bbs/issues/516) содержит меняющиеся и противоречащие друг другу наблюдения разных пользователей: это аргумент за измерение конкретной сети, а не за универсальный список. Уровень C, темы начаты 27.06.2025 и 07.09.2025; даты отдельных поздних комментариев нужно учитывать отдельно.

## 2. Принцип доступного посредника

При истинной блокировке всех пакетов к IP VPS нужна другая достижимая первая точка: relay, DNS resolver, edge CDN, свой/чужой разрешённый gateway. Потом эта точка достигает VPS по другому маршруту. Маскировка handshake сама по себе не создаёт такой путь.

Сейчас проверены (A): устройство → VK TURN → VPS; устройство → рекурсивный DNS → DNS VPS. Работоспособность VK при неработающем ping согласуется с этим механизмом, но одна эта пара наблюдений не доказывает вид блокировки прямого пути.

## 3. Сравнение решений

| Вариант | При истинной блокировке IP VPS | Внешняя зависимость | Решение для VPNN |
| --- | --- | --- | --- |
| Существующий VK TURN | Да, если VK endpoints/API и relay→VPS доступны | VK авторизация/лимиты/relay | Основной испытанный обходной путь, A |
| MasterDnsVPN | Да, если резолвер достигает делегированной зоны | Рекурсивный DNS, delegation | Резерв; ускорять по измерениям, A |
| Slipstream / DNSTT | По тому же DNS-принципу | DNS + новый серверный backend | Сравнительный стенд, B |
| AWG / VLESS Reality напрямую | Нет при полной IP-блокировке | Доступный прямой endpoint | Быстрый обычный режим, B |
| Hysteria2 / TUIC | Нет при полной IP-блокировке | Доступный UDP/QUIC | Резерв для других типов фильтра, не приоритет белых списков, B |
| XHTTP/WebSocket через CDN | Условно да через доступный edge | CDN, домен, поддерживаемое проксирование | Проверить сначала малый HTTPS control, затем транспорт, B |
| Cloudflare Tunnel | Условно: клиент должен достигать Cloudflare | Cloudflare + outbound connector VPS | Не универсальный резерв для РФ, B |
| SFU WebRTC/DataChannel/медиа | Условно да через медиасервер | Сигналинг/комната/SFU/авторизация | Первый новый relay-эксперимент, B |
| Доступный собственный gateway → VPS | Да, если gateway реально разрешён | Дополнительная точка размещения | Альтернатива вне ограничения одной VPS, D |
| Tor Snowflake/meek/WebTunnel | Условно, зависит от входного пути | Tor и bridges/proxies | Внешний аварийный канал доставки; не сразу встроенный VPN, B |
| Psiphon | Использует свою инфраструктуру и стратегии | Сеть Psiphon | Внешний recovery-путь, не протокол одной нашей VPS, B |
| TrustTunnel | Сам по себе нет | Достижимый endpoint | Отложить до доказанной пользы относительно уже имеющихся профилей, B |
| MASQUE CONNECT-UDP | Только через доступный proxy | Собственный/разрешённый MASQUE proxy | Механизм, а не готовый список доступных серверов, B |
| zapret/ByeDPI | Не устраняет полный IP drop | Проходимый маршрут и подходящее поведение DPI | Отдельная диагностика; не включать автоматически на Windows, B/D |

## 4. Самая полезная новая находка: SFU

[kulikov0/whitelist-bypass](https://github.com/kulikov0/whitelist-bypass) описывает headless Go/Pion на обоих концах, передачу через SFU с DataChannel или VP8-потоком и несколько платформ. Важна архитектура: оба конца общаются с медиасервисом; это отличается от TURN, которому разрешено пересылать UDP к произвольному VPS. **Это описание автора, не наше подтверждение доступности платформ в белом списке.**

Прототип: одна выбранная платформа, собственная комната, один клиент и серверный Go-процесс, loopback SOCKS, ограниченные тесты direct-blocked; затем два клиента и профилирование. Сначала DataChannel, media framing только если нужно и если допустим CPU/RAM. Не встраивать Electron/browser на VPS. Проверить license, pinned commit, защиту ключей, end-to-end аутентификацию/шифрование поверх посредника, повторную передачу, лимиты комнаты и индивидуальный отзыв. Наличие ChaCha20 «обфускации» в README не заменяет проверку криптографической аутентификации.

Поставщик конференции может видеть или завершать свои транспортные соединения; без собственного E2E слоя нельзя считать его слепым доверенным relay. Нужны socket protection и работа через нынешний TUN, а не второй VpnService из чужого приложения.

Порог перехода из R&D: работает при запрете прямого VPS, управляемая авторизация без постоянного браузера, 2 часа устойчивости, прирост доступности относительно VK, приемлемый расход из документа 04, безопасные ключи и отзыв. Смена комнаты/API остаётся зависимостью; гарантии «навсегда» нет.

## 5. Что поиск позволил исключить

[Good TURN](https://github.com/cacggghp/vk-turn-proxy) полезен как первичный источник TURN-архитектуры. В актуальном README старый Яндекс Телемост зачёркнут и есть отметка о закрытии. Поэтому старые статьи «Яндекс быстрее VK» не основание включать его готовым резервом.

[Lionheart](https://github.com/jaykaiperson/lionheart) в README отмечен архивом. Автор сообщает, что WB TURN запрещает пересылку на произвольные внешние IP. Это не опровержение другого SFU-проекта: TURN forwarding и передача между участниками через SFU — разные механизмы. Но Lionheart не рекомендован к интеграции как действующий транспорт.

Не принимать на веру «любой VPS в российском облаке находится в белом списке», «SNI известного сайта делает любой IP разрешённым», «ещё один домен на прежнем IP решит блокировку», «BBR ускоряет любой DNS/UDP», «включить сжатие HTTPS — получить кратный выигрыш».

## 6. CDN и обновление настроек

[XHTTP, обсуждение разработчика](https://github.com/XTLS/Xray-core/discussions/4113) описывает HTTP-транспорт и варианты CDN. Достижимый edge может отделить клиента от блокируемого origin. Нужно проверить конкретные режимы, buffering/timeouts, двустороннюю передачу и соответствие политики выбранного сервиса. Обычный CDN не автоматически проксирует WireGuard/произвольный UDP. Подмена SNI/Host без поддержки fronting самим CDN не создаёт relay.

[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/) даёт исходящий connector от сервера; это может убрать необходимость прямого клиентского доступа к origin. Но [Cloudflare 26.06.2025](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet) сообщал о российских ограничениях своих сервисов, включая короткие обрывающиеся передачи. Историческое сообщение не доказывает текущую ситуацию на каждой SIM, однако исключает Cloudflare как единственную гарантированную точку восстановления.

Практический порядок: доступность edge из целевых сетей → подписанный/зашифрованный маленький пакет настроек → только затем data-plane. Один контрольный ответ 200 недостаточен: нужны продолжительная передача и отсутствие обрыва после первых килобайт.

## 7. DNS и альтернативы

[MasterDnsVPN](https://github.com/masterking32/MasterDnsVPN) уже имеет resolver routing/ARQ; маркетинговое сравнение автора не переносить на VPNN. [Slipstream](https://github.com/EndPositive/slipstream) описывает QUIC multipath и adaptive congestion control. [Rust-вариант](https://github.com/Mygod/slipstream-rust) — отдельная реализация, не гарантированно взаимозаменяемая библиотека. [DNSTT mirror](https://github.com/Mygod/dnstt) полезен как контрольный вариант. Основной эксперимент описан в документе 04; замена сразу всей связки клиент/сервер не запланирована.

Запрошенная страница performance на bamsoftware.com вернула 403. Её цифры не использованы. Сравнительные скорости иных сетей не считать обещанием для МегаФона.

## 8. Tor и внешние recovery-пути

[Tor transports](https://support.torproject.org/tor-browser/circumvention/unblocking-tor/) предлагают разные способы входа. [Snowflake](https://snowflake.torproject.org/) использует временные прокси; механизм и ограничения исследованы в [USENIX Security 2024](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf). При строгом allowlist случайный IP добровольца тоже может быть недоступен; само слово WebRTC ничего не гарантирует. [WebTunnel](https://community.torproject.org/relay/setup/webtunnel/) требует доступного bridge; поднятый на том же полностью заблокированном IP не устраняет IP-блокировку.

Для VPNN разумнее сначала поддержать получение свежего файла через уже доступный внешний инструмент/устройство, чем добавить полный Tor в компактный APK. Возможность работы внешнего VPN рядом с VPNN ограничена одним системным VPN на Android; нельзя планировать два VpnService одновременно. Встроенный userspace recovery-прокси — отдельная будущая интеграция.

[Psiphon FAQ](https://www.psiphon.ca/en/faq) описывает собственный сервис обхода; это дополнительная внешняя зависимость, а не обещание доступа к нашей VPS без инфраструктуры Psiphon. [MASQUE RFC9298](https://www.rfc-editor.org/rfc/rfc9298.html) стандартизует UDP через HTTP-прокси, но не предоставляет доступный proxy сам по себе.

## 10. Приоритет исследований

1. Достоверно классифицировать сбой прямого пути на нужной SIM/сети; ping недостаточен.
2. Сделать существующий VK/DNS пригодным для восстановления настроек.
3. Нагрузочно подтвердить VK и подобрать DNS по реальному оператору.
4. Один headless SFU-прототип как новый первый hop, независимый от VK только если выбрана другая платформа.
5. Доступный CDN для малого config delivery; data-plane только после проверки.
6. Остальные механизмы — запасные направления. Не запускать всё одновременно на 1 ГБ.
