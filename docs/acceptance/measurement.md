# Протокол egress, CPU, RAM и goodput

## Доказательство egress

1. Согласовать независимый HTTPS endpoint вне VPS и инфраструктуры транспорта. Для каждого семейства IP отдельно установить ожидаемый публичный адрес исходящего соединения VPS по контрольному запросу с VPS и журналу приёмника. С того же клиентского процесса выполнить прямой контроль при выключенном туннеле и записать результат сравнения с VPS. При совпадении или неоднозначности нужен другой контрольный путь.
2. В изолированной тестовой среде запретить прямой TCP и UDP клиента до всех IPv4/IPv6 адресов VPS. Сохранить доступность разрешённого TURN, DNS или SFU. До запуска туннеля подтвердить запрет по счётчикам правила и активным пробам для обоих семейств с известным доступным до блокировки сервисом. Отсутствие ответа от UDP без контроля доступности недостаточно. Правило должно действовать всё окно. Для Windows и Honor любые ограничения применяет владелец на выделенном стенде или тестовом шлюзе.
3. Принудительно выбрать проверяемый маршрут, для Auto отдельно записать фактический путь. Независимый процесс отправляет по HTTPS новый случайный ID пробы и проверяет TLS, ответ, полезную нагрузку и отсутствие редиректа. Для системного теста процесс использует системную маршрутизацию без явного или унаследованного прокси. Для SOCKS указать явный прокси. Приёмник сверяет ID и фиксирует peer IP соединения без доверия к forwarded-заголовкам. Сопоставить время, маршрут, наблюдённый peer и ожидаемый egress по тому же семейству. Раздельно фиксировать семейство клиентской пробы и семейство, увиденное приёмником, если маршрут преобразует адреса.
4. Повторить пробу после Stop или управляемого разрыва проверяемого транспорта при прежнем правиле. Прежний VPS egress должен исчезнуть. Обычный выход после Stop может вернуться, если это ожидаемая политика. Зафиксировать DNS и IPv6 отдельно, включая отсутствие нежелательного прямого выхода. Снять только правила своего стенда.
5. Сохранить в обезличенной карточке булевы результаты контролей и тип egress. При отсутствии наблюдения приёмника, отрицательного контроля или проверенного запрета оставлять подтверждение blocked-direct egress открытым. Для прямого маршрута шаг с блокировкой не применяется. Ready, внешний IP из ответа без сверки, успешный звонок, ICMP и локальная передача по SOCKS сами по себе недостаточны для подтверждения системного egress. Исторический P1 оценивать по его исходному протоколу.

## План нагрузки

- **CAP-01.** Свежие 10 мин idle. Собрать read-only MemTotal/Available, swap, vCPU, CPU quota, диск/inode, состояние сети, drops, conntrack, cgroups и PSS/FD своих и legacy-служб. Для неизвестных значений использовать null. Записать версии пакетов и стенда, ограничения канала и квоты, режимы и число выдач.
- **CAP-02.** Измерить выдачи 2/4/8 без трафика, затем активные 1/2/4/8 для VK, DNS и смеси. Для SFU ступени задаются отдельным лимитом пилота. Применять отдельные тестовые назначения. Разделить idle выдачи, DNS backend на устройство, подключённые сессии без трафика, активные сессии и потоки внутри сессии. На ступень минимум три ограниченных повтора DL и UL отдельно, одна длительная передача, параллельно короткие HTTPS-запросы. Фиксировать число потоков, длительность, направление, объём, ограничения передачи и ошибки. Сохранять все повторы и порядок. Исключать прогрев по заранее заданному правилу.
- **CAP-03.** Синхронизировать общее окно измерений и счётчики на границах. На каждом узле измерять длительность монотонными часами. Снимать ряды с интервалом 1 с, если стоимость сбора допускает. Записать фактический интервал и пропуски. Считать RTT/TTFB p50/p95 и число проб, долю ошибок, повторы, ready sessions, per-client min/median, очереди, FD, drops и рестарты. При пропуске обязательной телеметрии повторить опыт.
- **CAP-04.** Порог пилота из плана — MemAvailable <200 MiB дольше 30 с. Остановить тестовую нагрузку при OOM, рестарте, устойчивом росте очередей или насыщении CPU с ростом p95 выше 2× сопоставимого контроля. До теста согласовать бюджет и способ остановки только тестовых генераторов. Предел определяется последней полностью пройденной ступенью с учётом худшего клиента, CPU, RAM, канала, ограничений relay и отзыва. Восемь выданных доступов не подтверждают восемь активных клиентов.
- **CAP-05.** На устойчивой ступени провести 2 ч, затем 24 ч смеси. Сверить baseline после освобождения сессий, память/FD, деградацию p95, refresh, limit и отзыв. Записать потерю доступа от начала отзыва отдельно от доставки receipt.

## Расчёт

| Метрика | Правило |
| --- | --- |
| Goodput | Байты проверенного прикладного payload на приёмнике в общем измерительном окне × 8 / длительность в секундах / 1 000 000. DL и UL отдельно. Агрегат — сумма полезных байтов всех клиентов за то же окно. Не складывать медианы индивидуальных скоростей. Исключить повторы, протокольные заголовки и данные вне окна. Записывать нулевую передачу и ошибки. Wire bytes считать отдельно. |
| CPU | Разность CPU time процесса или cgroup / стеновое время в тех же единицах даёт эквивалент занятых ядер. Умножить на 100 для процентов одного ядра. Записать baseline, raw и прирост, загрузку по ядрам, steal/softirq, throttling и эффективную квоту. При перезапуске не вычитать счётчики из разных экземпляров. Клиентские и серверные показатели хранить отдельно. |
| RAM | На VPS host MemAvailable и cgroup memory.current либо PSS по процессам при том же составе. Не складывать RSS для общего бюджета и не смешивать PSS с cgroup. На Honor использовать PSS, на Windows private working set с явной маркировкой. Для чисел в MiB делить байты на 2^20, KiB на 1024. Указать idle, median, peak, минимум MemAvailable и восстановление. |
| Стоимость сессии | Разность между сопоставимыми окнами с соседним числом сессий при одинаковых выдачах и профиле нагрузки, делённая на прирост числа сессий. Отдельно idle и active, Creator и Joiner, клиент и VPS. Хранить общий пик, включая общий overhead и фон. |

Для DNS записать запросы/ответы в секунду и запросы на MB полезной нагрузки, loss, reorder, RTT, SERVFAIL/TC, пустые ответы, очереди, in-flight и окно/MTU. При сравнении A/B/A сохранять одинаковый объём, резолвер, длину имени, шифрование, условия сети и нагрузку. Менять одну группу параметров. Учитывать разброс повторов и регрессии p95, ошибок и RAM. Для SFU дополнительно записать ограничения сессий, проверок, очередей и буферов, время освобождения ресурсов, справедливость по клиентам и причину каждого рестарта.
